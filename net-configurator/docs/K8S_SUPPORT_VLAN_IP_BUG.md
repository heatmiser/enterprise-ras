# Bug: k8s Support VLAN IP Allocation Outside Spreadsheet-Defined Subnet

## Summary

`excel_parser.py` hardcodes k8s node bond IPs starting at `.101` in the support subnet's
third-octet block, regardless of the prefix length the spreadsheet specifies for the support
network. When the spreadsheet defines a `/27` support subnet (as is typical), the auto-generated
k8s IPs fall outside that subnet, making them unreachable from the switch SVI gateway.

Discovered during Air simulation validation of the `2-8-5-200` kicktires site
(`ERA-ubuntu01-2-8-5-200`), August 2026.

## What the Spreadsheet Specifies

The Excel workbook defines the support VLAN subnet at the cluster level:

```
support_network:  10.78.220.32/27   ← switch SVI subnet (covers .32–.63)
support_gateway:  10.78.220.33      ← VRR gateway IP
```

The switch SVIs are generated from this:

| Switch   | SVI IP             | VRR IP            |
|----------|--------------------|-------------------|
| core-01  | 10.78.220.34/27    | 10.78.220.33/27   |
| core-02  | 10.78.220.35/27    | 10.78.220.33/27   |

## What the Spreadsheet Does NOT Specify

The k8s node bond IPs are **not in the spreadsheet**. They are auto-generated by
`excel_parser.py` using a hardcoded host offset of 101:

```python
# excel_parser.py ~line 983
host_offset = 101 + 2 * idx   # k8s-01 → .101, k8s-02 → .103, k8s-03 → .105
entry['bond_ip1'] = f"{base}.{host_offset}/24"
entry['bond_ip2'] = f"{base}.{host_offset + 1}/24"
```

For a `2-8-5-200` site with support_network `10.78.220.32/27`, this produces:

| Node     | bond_ip1            | bond_ip2            |
|----------|---------------------|---------------------|
| k8s-01   | 10.78.220.101/24    | 10.78.220.102/24    |
| k8s-02   | 10.78.220.103/24    | 10.78.220.104/24    |
| k8s-03   | 10.78.220.105/24    | 10.78.220.106/24    |

## Why This Breaks Connectivity

The generated IPs `.101`–`.106` fall in the `10.78.220.96/27` block (`.96`–`.127`), which is
a **different /27 than the switch SVI** (`10.78.220.32/27`, covering `.32`–`.63`).

Two failures result:

1. **k8s node routing policy never fires.** The netplan for each k8s node originally used:
   ```yaml
   routing-policy:
   - from: 10.78.220.32/27   # support_network passed from common
     table: 400
   ```
   Source traffic from `10.78.220.101` does not match `10.78.220.32/27`, so the `ip rule`
   for table 400 is skipped. Pings to the gateway go out `eth0` (OOB) instead of `bond0.400`.

2. **Switch cannot route replies back to k8s nodes.** The switch's VRF INBAND connected route
   covers only `10.78.220.32/27`. Packets sourced from `.101` arrive at the SVI, but the kernel
   on the switch has no route back to `.101` and drops the ICMP reply.

## Practical Impact

- k8s node VLAN 400 (support) traffic is completely non-functional on first deploy.
- GPU → k8s pings fail (GPU tries to reach k8s support IPs via VRF INBAND routing).
- k8s `_wait_gateway` loop burns 90 s per run waiting for an unreachable gateway, causing
  the ping-matrix script to exceed the playbook's 120 s collection window (NODATA).
- The lab team's spreadsheet is not at fault: `/27` for the switch SVI block is a reasonable
  allocation. The real hardware k8s nodes have no IPs yet — this tool is designing what they
  will receive.

## Workaround Applied to Current Simulation

Two live fixes were applied to `ERA-ubuntu01-2-8-5-200`:

**Core switches** (NVUE, both core-01 and core-02) — expand SVI to `/24` so VRF INBAND
can route to the `.101` range:
```
nv set interface vlan400 ipv4 address 10.78.220.3{4,5}/24
nv set interface vlan400 ipv4 vrr address 10.78.220.33/24
nv config apply --assume-yes; nv config save
```

**k8s nodes** (netplan) — change routing policy to match the node's actual source IP:
```bash
sudo sed -i 's|from: 10.78.220.32/27|from: 10.78.220.101/32|' /etc/netplan/10-netcfg.yaml
sudo netplan apply
```

The `air-deploy.py` code fix (routing-policy `/32`) is committed and will survive redeployment.
The switch SVI `/24` fix in the generated `host_vars` will be overwritten on regeneration until
the root cause is resolved (see below).

## Root Cause Fix Required

The fix belongs in **`excel_parser.py` around line 983**. Two acceptable approaches:

**Option A — Align k8s IPs to the support subnet prefix.**
Assign k8s bond IPs from within the subnet the spreadsheet defines, not at a hardcoded `.101`
offset that may fall outside it:
```python
# Derive host IPs from within support_base subnet, not a fixed offset
from ipaddress import ip_network, ip_address
net = ip_network(support_subnet, strict=False)
host_start = int(net.network_address) + 10  # leave first 9 for infra
entry['bond_ip1'] = f"{ip_address(host_start + 2 * idx)}/{net.prefixlen}"
```

**Option B — Require the spreadsheet to use a subnet that covers the intended IP range.**
Document (in `EXCEL_CONFIGURATION_GUIDE.md`) that `support_network` must be large enough
to contain both the switch SVIs and the k8s node host IPs. For a cluster where the code
places k8s IPs at `.101`+, the support_network must be at least a `/24`.

Option A is more robust (self-correcting regardless of spreadsheet prefix length).
Option B is simpler but relies on operator discipline.
